# SQL Server database implementation

This directory contains the complete physical implementation of all 34 finalized Day 1 relations for an independent educational used-car marketplace model. It does not claim to represent CARS24's internal production architecture.

## Environment target

Designed for Microsoft SQL Server 2025 (17.x) Express and SSMS 22. Uses T-SQL, `INT IDENTITY`, `DATETIME2`, `DECIMAL`, named constraints, filtered indexes, and SQL Server catalog views. No SQLCMD mode or file include directives are used.

## One-time SSMS workflow for a new database

1. Connect Object Explorer and the query window to `chakri\SQLEXPRESS` using the user's normal Windows authentication. Keep the query database set to `master`.
2. Open and execute `00_pre_execution_checks.sql`. It checks the server version and stops if `CARS24DataModelingSystem` already exists. It never drops or overwrites the database.
3. Only if the pre-check reports `READY`, open `00_run_complete_database_setup.sql` and execute it once. It is a self-contained generated T-SQL script with proper `GO` batch separators; it creates the database, all schemas/tables/constraints/indexes, seeds fixtures, and runs final validation. Its session-context gate raises an error and skips every DDL, seed, and validation batch when the SQL Server version or database-name precondition fails.
4. Review the Results and Messages tabs for errors and the final validation outputs. `11_post_execution_validation.sql` can be run separately afterward for a fresh diagnostic pass.

## Safe continuation for the existing database

The database creation script `01_create_database.sql` only runs `CREATE DATABASE` when `DB_ID` is NULL. It does not drop or overwrite a database, but it is a new-database entry point and does not make the rest of the implementation safe to rerun against populated tables.

For the existing `CARS24DataModelingSystem` database, connect SSMS to `chakri\SQLEXPRESS`, open `00_continue_database_setup.sql`, and execute it once. It does not include `01_create_database.sql`. Its first batch checks SQL Server version, target database existence/state/writability/compatibility; requires `VIEW DEFINITION`, `CREATE TABLE`, `CREATE SCHEMA` when needed, and `ALTER` on existing managed schemas; and reports the ten managed schemas plus the existing expected-table count. It stops before schema/table/index/seed DDL if any expected table/object name already exists, or if a managed schema contains any unexpected object. It reports partial or complete-looking models for manual review. If preflight passes, it runs the remaining canonical scripts in dependency order and ends with `11_post_execution_validation.sql`. Every gated batch uses `TRY/CATCH`; on a runtime error it closes the session gate and rethrows, so later `GO` batches are skipped.

Existing expected tables are deliberately treated as conflicts, including a partially built model. The script does not compare existing table definitions or attempt recovery; review any reported conflict manually before choosing a separate repair plan. Existing managed schemas without conflicting tables are accepted. The continuation script is generated by `generate_continuation_setup.ps1` and contains no SQLCMD includes.

## Source scripts and dependencies

Canonical SQL sources are files `01_create_database.sql` through `11_post_execution_validation.sql` (with `00_pre_execution_checks.sql` as a separate new-database preflight). The generated artifacts are `00_run_complete_database_setup.sql` and `00_continue_database_setup.sql`; do not edit those directly. The new-database master is generated from these canonical source files in dependency order:

1. `01_create_database.sql`
2. `02_create_schemas.sql`
3. `03_reference_tables.sql`
4. `04_core_tables.sql`
5. `05_vehicle_catalog.sql`
6. `06_vehicle_identity.sql`
7. `07_lifecycle_tables.sql`
8. `08_constraints.sql`
9. `09_indexes.sql`
10. `10_seed_reference_data.sql`
11. `11_post_execution_validation.sql`

Regenerate the new-database master after changing a source script with:

```powershell
.\database\generate_master_setup.ps1
```

The generated file is checked in for one-click review/execution. Do not edit it directly; regenerate it from the source files. The source scripts remain separately readable and guarded for object creation.

Regenerate the existing-database continuation after changing a source script with:

```powershell
.\database\generate_continuation_setup.ps1
```

## Architecture

| Schema | Purpose |
|---|---|
| `ref` | City reference |
| `core` | Branch, employee, and customer identities |
| `vehicle` | Brand/model/variant, identity, registration, ownership, submission |
| `inspection` | Inspection events, outcomes, checklist items, defects, valuations |
| `acquisition` | Seller offers, agreements, acquisition records |
| `inventory` | Current position and movement ledger |
| `marketplace` | Listing, image metadata, enquiry, reservation |
| `sales` | Sales order and vehicle detail |
| `finance` | Payment and refund attempts |
| `delivery` | Ownership transfer and vehicle handover |

Small controlled domains (fuel, transmission, statuses, outcomes, channels, and similar codes) stay as constrained code columns per Day 1. Currency and large reference domains are not expanded into extra entities. Source SQL documents row constraints separately from transaction/application rules.

## Validation

`11_post_execution_validation.sql` checks database and schema presence, expected table list/count (34), PK count (34), FK count (62), constraint/index metadata, seed counts, selected duplicate and temporal checks, and `DBCC CHECKCONSTRAINTS` for FK/check violations. A clean setup should have no missing/unexpected table rows, no disabled/untrusted FKs, no duplicate/temporal violation rows, and no `DBCC` violations.

The remaining setup and final validation have **not** been executed in SQL Server. SSMS confirmed the connected SQL Server version, and the database-creation script ran. Run the continuation script only after inspecting its preflight Results and Messages; a conflict result means it stopped before remaining DDL/seed batches.

## Constraints, indexes, and reference data

Primary keys, row-level checks, unique constraints, and defaults are declared with the table DDL. The implementation contains 34 primary keys, 62 foreign keys, 19 unique constraints, 79 check constraints, and 8 defaults. The index source defines 60 explicit indexes, including 7 unique or filtered indexes; with PK/UQ supporting indexes, the validation script expects 113 indexes total. FK lookup indexes are included where useful. The 10 controlled schemas contain the 34 Day 1 entities; controlled values such as fuel, transmission, statuses, and channels remain constrained code columns rather than extra reference entities. Synthetic reference and lifecycle fixtures are inserted parent-first with duplicate guards.

## Troubleshooting and limitations

- If continuation reports `NOT READY` or a conflict list, it has kept its session gate closed and skips all later DDL, seed, and validation batches. Review the listed objects in SSMS. Existing expected tables are never definition-matched or repaired automatically; partial and complete-looking models both require manual review.
- If the continuation reports insufficient catalog visibility, grant `VIEW DEFINITION` on the target database to the executing principal, then rerun its preflight.
- If the database is offline, read-only, below compatibility level 110, or the server is below major version 17, resolve the database/server configuration before continuing.
- If an error occurs after DDL begins, some earlier batches may already have committed. The failing batch closes the session gate and rethrows, so later batches are skipped. Do not rerun immediately: the next preflight will detect the created objects and stop for review.
- Cross-row temporal and workflow rules that cannot be expressed as row constraints (such as non-overlapping ownership intervals, multi-row refund limits, and matching lifecycle chains) are documented in SQL comments and require transactional/application validation.
- Day 1 documentation reports 59 ERD relationships while its finalized attributes declare 62 foreign keys; three relationships are absent from the logical ERD. Vehicle ownership is modeled only with customer references and cannot represent the company as an owner. These conceptual discrepancies remain documented and were not silently changed in Day 2.
