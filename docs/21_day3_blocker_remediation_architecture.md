## Findings from the third independent audit

## 1. Unified transaction and locking architecture

### Recommended common sequence

Use the same control flow in every phase:

1. Set `NOCOUNT` and `XACT_ABORT`; verify the database name and basic script preconditions that do not inspect mutable application rows.
2. Enter `TRY`, start the transaction, and acquire one **shared package resource** as an exclusive, transaction-owned application lock: `CARS24-Day3-Generation`.
3. Specify the same `@DbPrincipal` explicitly in all six scripts. Use identical resource spelling/case, lock mode and owner. Retain fail-fast timeout `0` unless operational review chooses a bounded wait. Treat every negative `sp_getapplock` return code as an error and roll back.
4. After lock acquisition, re-read all mutable prerequisites, deterministic-key conflicts, payload matches, cross-row conditions and expected prior lifecycle states. Use exact indexed key/range protection (`UPDLOCK,HOLDLOCK`) where a row or absent key must remain stable through the transaction. Make precondition reads use the same key definition as inserts/updates.
5. Apply inserts in parent-to-child order. Apply each update with both its deterministic key and expected prior values/status in the `WHERE` clause. Capture `@@ROWCOUNT` immediately and assert the exact expected number.
6. Run all postconditions and exact expected-payload/cardinality comparisons while the transaction and package lock are still active.
7. Commit only after every mandatory check succeeds. In `CATCH`, roll back whenever `XACT_STATE()<>0`, then rethrow. Do not print a success result before commit.

This single resource serializes all Day 3 phase transactions that cooperate with it, avoiding simultaneous phases and inconsistent lock-resource conventions. Individual phase transactions remain separate so a phase failure rolls back that phase without undoing earlier committed phases. A shared per-phase lock alone cannot enforce full workflow order across the commit gap; keep explicit phase dependency/state guards and the documented one-session, Phase 01-to-06 operator sequence. Calls can still interleave between committed phases, so each phase must be safely repeatable against its exact expected complete state or fail closed. Do not add a persistent phase ledger or schema object as part of this plan.

### Isolation, lock order, deadlocks, and non-cooperating writers

- The app lock coordinates only sessions requesting the same resource under the same database/principal scope. It does not protect against manual SQL, applications, jobs, or other scripts that do not request it.
- Use one order everywhere: transaction → package app lock → prerequisite parent keys → child/event keys → updates → postcondition reads. Within a phase, access tables in consistent parent-to-child order. This reduces, but cannot eliminate, deadlocks with external writers.
- Do not assume a whole-transaction `SERIALIZABLE` setting is automatically best. Prefer targeted `UPDLOCK,HOLDLOCK`/serializable key-range locks on exact predicates and supporting indexes for missing-row and temporal/cross-row uniqueness checks. Where no selective index exists, evaluate broader locks/table locking or require an approved quiet window. The chosen strategy must be checked against the actual execution plan and deployed indexes; these were not observed live.
- Make update predicates assert expected old owner, lifecycle, inventory, listing, submission or reservation state. A source check followed by an unconditional cohort update is not sufficient.
- A deadlock, lock timeout, unique-key violation or unexpected rowcount must abort and roll back the current phase. Retrying is an operator decision after checking current state; no automatic retry loop is proposed.
- Keep lock timeout fail-fast (`0`) as the default to avoid a queued operator run proceeding after stale assumptions. If a wait timeout is selected, it must remain finite and all negative lock returns remain fatal.

## 2. Independent final validator design

### Expected-row construction and comparison contract

The final validator should construct expected rows from a separate, read-only specification of the documented cohort formulas, without reading phase result messages, inserted/skipped counts, or success flags. Prefer explicit `VALUES`/number CTEs and deterministic derivation from Day 3 ordinal keys, fixture natural keys and timestamps. Resolve identity IDs by expected natural keys, then compare both sides of each family:

- Expected-to-actual left anti-join: every expected key exists exactly once and all expected non-identity payload columns equal.
- Actual-to-expected left anti-join: no unexpected Day 3 key/payload rows.
- Per-key grouping: no duplicate logical event keys even if table count is correct.
- Relationship checks: all expected foreign-key parents resolve to the expected parent key, not merely any valid FK target.
- Preserve identity values as opaque generated IDs; assert their links, not their numeric values.
- Null-safe compare nullable columns using explicit `IS NULL` pairs or null-safe normalization with a sentinel that cannot be a valid value. Avoid relying on `<>` where NULL would yield UNKNOWN.
- Keep Day 2 baseline rows in a separate fixture specification and do not treat them as D3 expected rows.

Expected formulas must be documented/versioned independently from phase success output. During implementation, a reviewer should reconcile the independent specification to the user-approved Day 3 plan and source formulas; tests should deliberately mutate/miss/substitute a row in a disposable offline model or parser harness if one already exists. No such execution is authorized by this plan.

### PASS / FAIL / WARNING policy

- **PASS:** target database identity is correct; strict fixture gate passes; every expected D3 row exists exactly once; expected-to-actual and actual-to-expected payload comparisons are empty; all expected relationships/lifecycle states/counts pass; no unexpected D3 namespace rows; FK/CHECK/index health and DBCC checks report no issue; all required metadata is visible.
- **FAIL:** any missing, duplicate, unexpected, mismatched payload, wrong relationship/state/count, integrity finding, object-health issue, inaccessible/incomplete catalog visibility, DBCC error, or database identity/state mismatch. A runtime SQL error must abort before any PASS output.
- **WARNING:** informational diagnostics only (e.g., server/product/compatibility metadata, validation timestamp, DBCC's documented non-exhaustive scope). Warnings never suppress or convert a FAIL. A warning about unverified rules must be stated alongside PASS and cannot be read as execution readiness.

## 5. Acceptance criteria

The architecture work is acceptable for a future implementation only when:

1. Every generation phase takes the same package lock before mutable checks and writes, inside its transaction; exact state predicates and rollback-on-failure remain in force.
2. Cross-phase dependencies are explicit; operating guidance still requires Phase 01–06 order; package locking behavior and interleaving limits are documented.
3. Preflight's Day 2 fixture, structural and integrity checks all contribute to a single fail-closed readiness result and remain read-only.
4. The final validator compares all generated families against independently derived expected full payloads and rejects missing, duplicate, unexpected or altered rows; DBCC limitations are stated.
5. The Day 2 seed and schema fixture is compared by values and relationships, not only counts or identity numbers.
6. Static/parser checks and an independent audit complete with no unresolved high/critical issue. No claim of database readiness or generation authorization is made.
